# Task 4.5 — Property 5: Technical Claim Traceability

**Property:** *For every* klaim teknis `K` di `Skripsi/bab3_metodologi.md`, terdapat
minimal satu rujukan kode `R` yang menyertai `K` dengan format `path:simbol` atau
`path:start-end`; berkas yang ditunjuk benar-benar ada di `src/`, `Cargo.toml`,
`.cargo/config.toml`, `examples/*/src/`, `tests/`, atau `assets/`; dan simbol
yang dirujuk benar-benar terdefinisi pada berkas tersebut.

**Validates:** Requirements 13.1, 13.2, 13.3, 13.4, 13.5, 13.6, 13.7, 13.8,
13.9, 13.10, 13.11, 13.12, 15.1, 15.2, 15.3, 15.4, 15.5.

## Methodology

1. Ekstraksi otomatis seluruh referensi backtick berbentuk
   `` `path.ext` `` atau `` `path.ext:spec` `` dengan ekstensi `rs`, `toml`,
   `frag`, atau `vert` melalui skrip Python
   [`4.5-extract-refs.py`](./4.5-extract-refs.py).
2. Untuk setiap referensi, verifikasi:
   - File path eksis pada `src/`, `Cargo.toml`, `.cargo/config.toml`,
     `examples/*/src/`, `tests/`, atau `assets/`.
   - Bila spec berupa `N` (line tunggal): `1 ≤ N ≤ total_lines(file)`.
   - Bila spec berupa `N-M` (range): `1 ≤ N ≤ M ≤ total_lines(file)`.
   - Bila spec berupa simbol: simbol terdefinisi sebagai
     `fn|struct|enum|trait|const|static|type` di Rust, atau sebagai fungsi
     GLSL `name(...)` di shader, atau muncul sebagai token literal di TOML.
   - Bila path tidak ditemukan apa adanya tetapi merupakan basename tunggal
     (mis. `render_tile.frag`), pencarian fallback memetakannya ke berkas
     yang ada di repositori (kategori `OK_BASENAME`).
3. Ekstraksi dijalankan dengan `python 4.5-extract-refs.py --out 4.5-output.md`
   (output UTF-8 mentah). Skrip pendamping `spot_check.py` dijalankan via
   `python spot_check.py` untuk mengonfirmasi konten baris pada referensi
   kuratorial.
4. Pemetaan referensi ke subbab dilakukan dengan menelusuri heading
   Markdown `## 3.x` dan `### 3.x.y` saat membaca dokumen baris-per-baris,
   sehingga setiap referensi dilabeli dengan subbab terdekat di atasnya.

### Catatan Scope Subbab 3.1, 3.2.x, dan 3.4.1

Subbab 3.1 (kerangka berpikir penelitian), 3.2.x (analisis user, aplikasi sejenis,
rumusan kebutuhan), dan 3.4.1 (enumerasi naratif tiga use case UC-01/02/03)
tidak memuat klaim teknis yang menyebut nama berkas, fungsi, struct, atau
parameter numerik konkret pustaka Arabella. Hal ini konsisten dengan dua
batasan eksplisit dokumen:

1. **Definisi scope traceability di paragraf pengantar Subbab 3.3** (baris 61
   `Skripsi/bab3_metodologi.md`):
   > "Setiap klaim teknis pada Subbab 3.3 sampai 3.7 wajib dapat ditelusuri
   > langsung ke source code melalui rujukan kode berformat `berkas:simbol`
   > atau `berkas:start-end`…"

   Kewajiban traceability dengan demikian dibatasi pada rentang Subbab 3.3
   sampai 3.7. Subbab 3.1 dan 3.2.x berada di luar scope ini secara desain.

2. **Requirement 14.1** ("Ruang Lingkup Revisi yang Dipertahankan") yang
   mewajibkan Subbab 3.1 dan 3.2 dipertahankan dari Bab_3_Lama tanpa
   perubahan kata maupun urutan kalimat (kecuali patch referensi silang
   terminologi). Karena teks lama tidak memuat rujukan kode berformat
   `path:simbol`, penambahan rujukan akan melanggar Req 14.1.

3. **Subbab 3.4.1** memuat tiga deskripsi naratif UC-01/02/03 berupa kalimat
   pendek tanpa klaim teknis spesifik (tidak menyebut nama fungsi atau
   konstanta). Detail teknis UC-03 dirinci secara penuh pada Subbab 3.4.2
   (Use Case Description), yang memuat tujuh rujukan kode tervalidasi.

Karena tidak ada klaim teknis pada subbab-subbab tersebut, tidak ada referensi
kode yang perlu diverifikasi, dan kondisi PASS tetap terpenuhi sesuai definisi
property: predikat universal "untuk setiap klaim teknis K" bernilai vacuously
true bila himpunan klaim teknisnya kosong.
